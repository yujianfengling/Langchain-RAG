## 2. 多模态 Document 有效性审查

### 2.1 核心问题：两条转换路径存在架构断裂

V2.3.0 存在**两条独立的 Document 转换路径**，且未互通：

```
路径 A（Loader Pipeline，当前生产路径）:
  PdfLoader
    → PDFAnalyzer.analyze()
    → PDFElement(text/image/formula/table)
    → DocumentAdapter.adapt()
    → TextAdapter / ImageAdapter / FormulaAdapter / TableAdapter
    → LangChain Document
    ⚠️ 不经过 MultimodalDocumentConverter

路径 B（MultimodalDocumentConverter，设计但未集成）:
  MultimodalDocumentConverter.convert_elements()
    → PDFElement → MultimodalDocument
    → multimodal_service.enrich_multimodal_document()
    → 视觉分析 / OCR / 表格提取
    → MultimodalDocument.to_langchain_document()
    → LangChain Document（含 modality / model_used / description / ocr_text）
    ⚠️ 未被 Loader Pipeline 调用
```

**`rag_service.py` 第 91 行**导入了 `MultimodalDocumentConverter`，但 `load_documents_from_directory`（Loader Pipeline）实际走的是路径 A。路径 B 的富化逻辑从未在生产流程中执行。

### 2.2 image 类型 Document 严重缺陷

**当前 page_content**:
```
[图片] | 尺寸: 898x401 | 页码: 4
```

**缺失信息**:
- ❌ 无图片描述（视觉模型分析结果）
- ❌ 无 OCR 文本
- ❌ 无文件路径（metadata 中有 image_xref 但无保存路径）
- ❌ 无 `modality` 字段
- ❌ 无 `model_used` 字段

**影响**: 146 个 image Document 完全无法被语义检索命中。用户问"电路图"或"光路图"时，这些图片 Document 不会被返回。

**对比**：路径 B 的 `MultimodalDocumentConverter` 可以生成：
```python
{
    "type": "image",
    "modality": "image",
    "description": "这是一个简谐运动的波形图...",
    "model_used": "qwen-vision",
    "ocr_text": "...",
    "model_confidence": 0.95
}
```
但这段逻辑从未在生产路径中执行。

### 2.3 table 类型 Document 部分有效

**当前 page_content**:
```
[表格] | 尺寸: 5行x5列 | 页码: 8 | 预览: | 变量关系 | 内能增量ΔE | 热量Q | 功A; 等体过程 dV = 0 ...
```

**评估**:
- ✅ 包含表格预览文本（可检索）
- ✅ 包含行列数信息
- ⚠️ 预览文本可能截断（仅预览前几行）
- ❌ 无 `modality` 字段
- ❌ 路径 B 的 `table_extractor`（Camelot/PDFPlumber）未被调用，表格结构未被解析

### 2.4 formula 类型 Document 基本有效

**当前 page_content**:
```
[公式] | 原始: § 8.2平衡态理想气体状态方程一、气体的状态参量...
```

**评估**:
- ✅ 包含公式周围上下文文本（可检索）
- ✅ `formula_type` 字段区分了 display/inline
- ⚠️ 实际公式内容（LaTeX/MathML）在 `content` 字段中，但 page_content 只用 `[公式]` 标记
- ❌ 无 `modality` 字段

### 2.5 metadata 字段不统一

| 字段 | text | formula | image | table | MultimodalDocumentConverter |
|------|------|---------|-------|-------|----------------------------|
| type | ✅ | ✅ | ✅ | ✅ | ✅ |
| modality | ❌ | ❌ | ❌ | ❌ | ✅ |
| model_used | ❌ | ❌ | ❌ | ❌ | ✅ |
| description | ❌ | ❌ | ❌ | ❌ | ✅ |
| ocr_text | ❌ | ❌ | ❌ | ❌ | ✅ |
| is_inline | ❌ | ✅ | ❌ | ❌ | ❌ |
| formula_type | ❌ | ✅ | ❌ | ❌ | ❌ |

**结论**: 路径 A（生产路径）和路径 B（MultimodalDocumentConverter）的 metadata schema 完全不一致。

## 3. Embedding Batch 方案架构审查

### 3.1 当前实现

`BatchedHuggingFaceEmbeddings` 位于 `rag/embedding.py`，是对 `HuggingFaceEmbeddings` 的包装器：
- `embed_documents()`: 分批处理（batch_size=64），解决 sentence-transformers 5.6.0 批量处理兼容性问题
- `embed_query()`: 直接委托给内部模型

### 3.2 架构评估

**应该留在 `embedding.py` 的理由**:

1. **职责归属正确**: `BatchedHuggingFaceEmbeddings` 是 Embedding 模型的包装器，实现了 `langchain_core.embeddings.Embeddings` 接口。它的职责是"将文本转换为向量"，这正是 `embedding.py` 的职责。

2. **`vector_store.py` 职责不同**: `vector_store.py` 负责 FAISS 向量存储操作（创建、加载、添加文档、相似度搜索）。它**使用** Embedding 模型，但不应**包含** Embedding 模型实现。

3. **依赖方向正确**:
   ```
   vector_store.py → embedding.py (使用 Embedding 接口)
   embedding.py → HuggingFaceEmbeddings (包装底层实现)
   ```

4. **单一职责**: 如果把 `BatchedHuggingFaceEmbeddings` 移到 `vector_store.py`，会导致 `vector_store.py` 同时负责"向量存储"和"Embedding 模型管理"两个职责。

### 3.3 建议

**✅ 当前位置（`embedding.py`）正确，不需要移动。**

可选改进：
- 将 `batch_size=64` 提取为配置参数（当前硬编码）
- 在 `config/models.py` 中增加 `embedding_batch_size` 配置项

## 4. Document Fusion 设计评估

### 4.1 当前粒度分析

| 指标 | 值 |
|------|-----|
| 总 Document 数 | 2917 |
| PDF 数量 | 9 |
| 平均每 PDF Document 数 | 324 |
| 最大 PDF Document 数 | 1731（《大学物理》习题-解答2025.03.pdf） |
| 最小 PDF Document 数 | 52（第六章习题解答.pdf） |

### 4.2 是否"过碎"？

**结论：当前粒度基本合理，但存在优化空间。**

**合理的理由**:
1. **text 类型（2195 个）**: 大学物理教材的每个段落/知识点是一个独立的 text 元素。这是合理的——用户问"什么是理想气体状态方程"时，应该返回精确的段落，而不是整章内容。
2. **formula 类型（570 个）**: 公式需要独立存储以支持精确检索。用户问"抛体运动公式"时，不应返回整页文本。
3. **image 类型（146 个）**: 图片本身需要独立 Document（待富化后）。

**过碎的证据**:
1. 部分 text Document 内容极短（如 "m — 气体的质量；M — 气体的摩尔质量"），仅为列表项。
2. 同一公式的上下文文本被重复存储在 formula Document 中。

### 4.3 Element Fusion 方案评估

**不建议在 V2.3.1 实施全局 Element Fusion 的理由**:

1. **formula + text 合并会降低检索精度**: 如果把公式和周围文本合并，用户搜"理想气体状态方程"时会返回包含大量无关文本的 Document，降低 RRF 排序效果。
2. **image 当前无内容可融合**: 146 个 image Document 的 page_content 仅为 `[图片] | 尺寸: ...`，合并到 text 中没有意义。
3. **BM25 检索器依赖短文本**: BM25 基于词频统计，短而精确的 Document 更适合 BM25 检索。

### 4.4 推荐方案：Page-Level Fusion 作为可选策略

**V2.3.1 建议**:

```
策略 1（默认）: 保持当前 Element-Level 粒度
  - text / formula / image / table 各自独立
  - 适用于精确检索场景

策略 2（可选）: Page-Level Fusion
  - 同一页的 text + formula 合并为一个 Document
  - image / table 保持独立
  - 适用于需要更多上下文的场景
  - DocumentAdapter 已有 merge_documents(strategy='group_by_page') 方法

策略 3（高级）: Semantic Fusion
  - 基于语义相似度合并相邻 text 段落
  - 需要 Embedding 计算，仅在构建索引时执行
  - 适合 V2.4.0+
```

**关键前提**: 在实施任何 Fusion 策略之前，必须先解决 image Document 无内容的问题（第 2.2 节）。否则融合无意义。

## 6. V2.3.1 建议方案

### 6.1 核心目标：打通多模态数据流

**架构修改**:
```
PdfLoader
  → PDFAnalyzer.analyze()
  → PDFElement(text/image/formula/table)
  → DocumentAdapter.adapt()          ← 现有路径
    → TextAdapter / FormulaAdapter / TableAdapter（保持不变）
    → ImageAdapter（改造：调用 MultimodalDocumentConverter）
  → 输出：含 modality / description / ocr_text 的完整 Document
```

### 6.2 具体任务

1. **改造 ImageAdapter**: 在 `adapt()` 方法中调用 `MultimodalDocumentConverter` 进行图片富化
2. **统一 metadata schema**: 所有 Adapter 输出的 Document 必须包含 `modality` 字段
3. **Table 预览增强**: 确保表格完整内容被提取（不只是前几行）
4. **batch_size 配置化**: 从 `config/models.py` 读取 `embedding_batch_size`

### 6.3 不修改的内容

- ❌ 不修改 PDFAnalyzer（检测器层）
- ❌ 不修改 FormulaAdapter（公式处理已基本可用）
- ❌ 不修改 TextAdapter（文本处理已正常）
- ❌ 不修改 Embedding 模型（BatchedHuggingFaceEmbeddings 已修复）
- ❌ 不实施 Element Fusion（需更多评估）
