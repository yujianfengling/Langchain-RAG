# 智慧教育系统项目 Skill 使用策略

## 1. Skill 调用规则

### 1.1 默认启用技能（代码重构阶段）

以下技能在代码重构阶段**默认启用**，每个任务都会自动调用：

| 技能名称 | 作用 | 启用原因 |
|---------|------|----------|
| `software-engineering-discipline` | 提供系统化的软件工程工作流程，包括理解、计划、实现、验证等7个步骤 | 确保重构过程遵循工程规范，避免混乱 |
| `superpowers-writing-plans` | 帮助制定详细的重构计划，包含风险评估和依赖映射 | 复杂重构需要明确的计划，避免遗漏关键点 |
| `openhands-code-review` | 对代码变更进行结构化审查，识别逻辑错误和最佳实践违反 | 重构后必须进行代码审查，确保质量 |
| `runesleo-systematic-debugging` | 系统化的调试流程，避免猜测性修复 | 重构过程中遇到问题时，用科学方法定位根本原因 |
| `superpowers-verification-before-completion` | 完成前全面验证，运行测试和功能检查 | 确保重构不破坏现有功能 |

### 1.2 按需启用技能（特定触发条件）

以下技能仅在满足特定条件时启用：

| 技能名称 | 触发条件 | 使用场景 |
|---------|----------|----------|
| `rag-skill` | 修改 `rag_engine.py` 或检索流程相关文件时 | 优化RAG检索策略、调整Embedding模型、改进文档切分 |
| `fastapi` | 修改API接口相关文件时（如 `app.py`、路由文件） | 新增/修改FastAPI端点、调整请求/响应模型、优化中间件 |
| `testing-python` | 修改代码后需要验证时 | 编写/运行pytest测试用例、检查测试覆盖率 |
| `fix-build-agentops-testing-python` | 测试失败需要修复时 | 分析测试失败原因、修复测试代码、确保测试通过 |
| `agent-browser` | 需要验证前端界面时 | 测试Gradio界面交互、验证API端点响应 |
| `code-review` | 重大功能完成后需要深度审查时 | 进行更严格的代码质量检查 |
| `superpowers-brainstorming` | 遇到复杂问题需要探索多种解决方案时 | 收集上下文、进行结构化头脑风暴 |
| `superpowers-executing-plans` | 执行复杂重构计划时 | 按照计划逐步执行，保持纪律 |
| `openhands-technical-writing` | 需要更新文档或注释时 | 重写代码注释、更新README、编写技术文档 |
| `openhands-uv` | 需要安装/更新Python依赖时 | 使用uv管理虚拟环境和依赖 |
| `skill-creator` | 需要创建新技能时 | 开发针对项目的自定义技能 |
| `find-skills` | 需要发现新技能时 | 搜索和安装新的Agent技能 |

### 1.3 暂时禁用技能（当前阶段不使用）

以下技能在代码重构阶段**暂时禁用**，避免干扰重构工作：

| 技能名称 | 禁用原因 |
|---------|----------|
| `ui-ux-design-pro` | 当前优先解决代码结构问题，不修改UI |
| `openhands-frontend-design` | 同上，UI重构延后 |
| `openhands-theme-factory` | 同上，主题定制延后 |
| `pptx` | 项目不需要制作演示文稿 |
| `pdf` | 项目不需要处理PDF文件 |
| `docx` | 项目不需要处理Word文档 |
| `xlsx` | 项目不需要处理Excel文件 |
| `多模态内容生成` | 项目不涉及多媒体内容生成 |
| `playwright-cli` | 项目不需要浏览器自动化测试 |

## 2. 当前重构阶段执行流程

### 阶段概述

代码工程化重构阶段，重点解决：
1. 代码结构混乱问题
2. 缺乏模块化设计
3. 错误处理不完善
4. 缺少类型注解
5. 测试覆盖率不足

### 标准执行流程

```
┌─────────────────────────────────────────────────────────────┐
│                    代码重构标准流程                           │
├─────────────────────────────────────────────────────────────┤
│  1. 理解阶段 (Understanding)                                │
│     ├── 使用 software-engineering-discipline                │
│     ├── 阅读相关代码文件                                     │
│     ├── 识别代码异味和问题                                   │
│     └── 分析依赖关系                                        │
│                                                             │
│  2. 计划阶段 (Planning)                                     │
│     ├── 使用 superpowers-writing-plans                       │
│     ├── 制定重构计划（目标、步骤、风险）                       │
│     ├── 识别受影响的模块                                     │
│     └── 确定回滚策略                                        │
│                                                             │
│  3. 实现阶段 (Implementation)                               │
│     ├── 使用 superpowers-executing-plans                    │
│     ├── 按计划逐步重构                                      │
│     ├── 保持小步快跑，频繁提交                               │
│     └── 及时记录变更                                        │
│                                                             │
│  4. 审查阶段 (Review)                                       │
│     ├── 使用 openhands-code-review                          │
│     ├── 检查代码质量                                        │
│     ├── 验证是否符合规范                                     │
│     └── 识别潜在问题                                        │
│                                                             │
│  5. 验证阶段 (Verification)                                 │
│     ├── 使用 superpowers-verification-before-completion     │
│     ├── 运行现有测试                                        │
│     ├── 手动测试关键功能                                     │
│     └── 确保无回归问题                                       │
│                                                             │
│  6. 调试阶段 (Debugging) - 如有问题                         │
│     ├── 使用 runesleo-systematic-debugging                  │
│     ├── 收集症状信息                                        │
│     ├── 隔离问题                                            │
│     └── 验证修复                                            │
│                                                             │
│  7. 测试阶段 (Testing) - 代码变更后                         │
│     ├── 使用 testing-python                                 │
│     ├── 编写单元测试                                        │
│     ├── 运行测试套件                                        │
│     └── 检查覆盖率                                          │
└─────────────────────────────────────────────────────────────┘
```

### 具体操作指南

#### 2.1 开始重构任务前

1. **明确重构目标**：定义要解决的具体问题
2. **评估影响范围**：确定哪些模块会受影响
3. **制定备份策略**：确保可以回滚到之前状态
4. **通知团队成员**：避免冲突（如适用）

#### 2.2 重构执行中

1. **小步提交**：每个小改动单独提交，便于追踪
2. **保持测试通过**：每次提交前确保测试通过
3. **及时记录**：记录所做的更改和原因
4. **定期审查**：每完成一个逻辑单元就进行代码审查

#### 2.3 重构完成后

1. **全面测试**：运行完整测试套件
2. **代码审查**：进行最终代码审查
3. **文档更新**：更新相关文档和注释
4. **性能验证**：确保性能没有显著下降

## 3. 后续开发规范

### 3.1 代码规范

#### 命名规范
- **变量/函数**：`snake_case`（Python标准）
- **类名**：`CamelCase`
- **常量**：`UPPER_SNAKE_CASE`
- **私有成员**：以单下划线开头 `_private_var`

#### 代码结构
- **模块化**：每个功能模块独立文件
- **单一职责**：每个函数/类只做一件事
- **依赖注入**：通过参数传入依赖，便于测试
- **类型注解**：所有公共API必须添加类型注解

#### 错误处理
- **具体异常**：捕获具体异常类型，避免裸 `except`
- **错误传播**：合理使用 `raise` 传播错误
- **日志记录**：使用 `logging` 模块记录错误
- **优雅降级**：提供合理的默认值或备选方案

### 3.2 提交规范

#### 提交信息格式
```
<type>(<scope>): <subject>

<body>

<footer>
```

#### 类型（type）
- `feat`：新功能
- `fix`：修复问题
- `docs`：文档更新
- `style`：代码格式调整
- `refactor`：代码重构
- `test`：测试相关
- `chore`：构建/工具链更新

#### 示例
```
refactor(rag): 重构文档加载器模块

- 将文档加载逻辑拆分为独立类
- 添加类型注解
- 改进错误处理

Closes #123
```

### 3.3 审查流程

#### 审查清单
1. **功能正确性**：代码是否按预期工作？
2. **代码质量**：是否遵循项目规范？
3. **错误处理**：异常处理是否完善？
4. **测试覆盖**：是否有足够的测试？
5. **性能影响**：是否有性能问题？
6. **安全性**：是否存在安全隐患？

#### 审查工具使用
- **日常审查**：使用 `openhands-code-review`
- **深度审查**：使用 `code-review`
- **安全审查**：使用 `openhands-security`（按需）

### 3.4 测试要求

#### 测试策略
- **单元测试**：每个模块必须有单元测试
- **集成测试**：关键流程必须有集成测试
- **端到端测试**：核心功能必须有E2E测试

#### 测试覆盖率
- **目标覆盖率**：≥80%
- **关键模块**：≥90%
- **新代码**：必须包含测试

#### 测试工具
- **测试框架**：pytest
- **覆盖率工具**：pytest-cov
- **测试运行**：使用 `testing-python` 技能

### 3.5 文档要求

#### 代码文档
- **模块文档**：每个模块必须有文档字符串
- **函数文档**：所有公共函数必须有文档字符串
- **类文档**：所有类必须有文档字符串
- **复杂逻辑**：必须添加行内注释

#### 项目文档
- **README**：保持更新，包含安装和使用说明
- **API文档**：FastAPI自动生成，但需确保描述准确
- **架构文档**：记录关键设计决策

### 3.6 版本控制

#### 分支策略
- `main`：稳定版本
- `develop`：开发分支
- `feature/*`：功能分支
- `fix/*`：修复分支
- `refactor/*`：重构分支

#### 合并策略
- **功能分支**：必须通过代码审查才能合并
- **重构分支**：必须通过全面测试才能合并
- **修复分支**：必须验证修复有效才能合并

## 5. 策略调整机制

### 定期评估
- **每周评估**：检查技能使用效果
- **阶段评估**：每个重构阶段结束后评估
- **按需调整**：根据实际情况随时调整

### 调整依据
- **效率提升**：技能是否提高了开发效率？
- **质量改善**：技能是否改善了代码质量？
- **团队反馈**：团队成员对技能的评价？
- **项目需求**：项目阶段变化是否需要调整？

### 调整流程
1. **识别问题**：发现技能使用中的问题
2. **分析原因**：分析问题产生的原因
3. **制定方案**：制定调整方案
4. **实施调整**：更新技能使用策略
5. **验证效果**：验证调整效果
