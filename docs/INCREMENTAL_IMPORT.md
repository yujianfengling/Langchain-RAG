# 增量导入：增量解析与向量化 vs 索引整体重组（2026-10-08）

## 一句话区分

| | 增量**解析与向量化** | 索引**整体重组** |
|---|---|---|
| 做什么 | 只对**新增/变化**的资料做抽取、分块、编码 | 把该学科的全部 chunk 重新写入 FAISS/BM25 文件 |
| 是否调用模型 | **未变化的分块 0 次调用**（命中向量缓存） | 不调用模型（只用已有向量） |
| 是否仍发生 | 只有变化的部分发生 | **每次导入仍然发生** |
| 代价 | 与变化的资料量成正比 | 与学科总 chunk 数成正比（13k 块约 10 分钟）|

**结论**：本轮实现的是**增量解析与向量化**——模型调用被省掉了；
FAISS/BM25 索引文件**仍是整体重组**（本项目用 IndexFlatL2 + 全量写文件，不是可增删索引结构）。
所以入库等待时间显著下降，但整库重组这一步仍在。

## 机制

1. **资料级解析缓存**（既有，本轮沿用）：data/cache/parsed_docs/<内容哈希>_<解析配置>.json。
   内容哈希 + 解析器版本 + 视觉配置共同决定键，未变化资料不重新解析、不重新识图。
2. **chunk 级向量缓存**（本轮新增，rag/embedding_cache.py）：
   data/cache/embedding_cache.db（SQLite，key = sha256(缓存schema | 模型签名 | 分块正文)）。
   建库时先按 chunk 查缓存，命中即复用向量，只有 miss 才调用 Embedding。
   换 embedding 模型 → 模型签名变化 → 键失效 → 全部重编码（不会拿旧模型向量冒充）。
3. **修改 = 替换**：同名不同内容不再另存为副本，而是把旧文件移入
   <学科>/_superseded/<文件名>.<旧内容哈希前12位> 留档，新文件写回原名。
   旧分块随之从下一次建库中消失，不会新旧版本同时被召回；留档目录不参与建库
   （建库只扫学科根目录下的文件）。取消/失败时会从留档恢复旧文件。
4. **删除**：DELETE /knowledge/{subject_id}/documents/{filename} 删文件并重建，
   一次性把该资料的分块与来源从索引中撤除。

## 实测（隔离学科，5 份 txt；同文件同条件，冷/热不混比）

EMBEDDING_CACHE=0 等价于改动前的整库重编码，=1 为增量：

| 阶段 | 耗时(前→后) | 实编码分块(前→后) | 缓存命中(后) |
|---|---|---|---|
| 首次导入 5 份（冷） | 12.3s → 11.5s | 5 → 5 | 0 |
| 新增 1 份 | 2.1s → **0.6s** | **6 → 1** | 5 |
| 修改 1 份 | 2.1s → **0.6s** | **6 → 1** | 5 |
| 原样重传 | 1.9s → **1.1s** | **6 → 0**（0 次模型调用） | 6 |

解析侧本来就已是增量（后续阶段 parse_ms 仅约 300ms），本轮把向量化也变成增量。

## 已知限制

- 索引文件仍是整体重组（约 10 分钟/13k 块）；真正可增删的索引结构是后续优化。
- 向量缓存按分块正文 + 模型签名，不含切分配置；但切分配置变化会引起分块正文变化，从而自然失效。
- 缓存只增不删；删除缓存只会导致一次全量重编码，不影响正确性。
## 大库（莫大物化，92 份 / 13,109 块）实测阶段归属（2026-10-08 晚）

同资料、同条件（重传一份已有资料触发一次完整建库），逐次记录：

| 轮次 | 条件 | 墙钟 | build_ms | embed_ms | 实编码分块 |
|---|---|---|---|---|---|
| 上一轮（无任何缓存） | 全冷 | 611s | 611,000 | — | 13,109 |
| 第 1 次 | 解析热 / 向量冷 | 365.9s | 363,958 | **315,616（87%）** | 13,109 |
| 第 2 次 | 向量热 / 分词冷 | 44.8s | 43,526 | 0 | 0 |
| 第 3 次 | 向量热 / 分词首次填充 | 53.9s | 52,878 | 0 | 0 |
| 第 4 次 | **全部热（稳态）** | **9.7s** | **6,114** | 0 | **0** |

结论：
- **瓶颈是 embedding**（冷态占 build 的 87%，315.6s），**不是 FAISS**。
  同一批数据的 FAISS 构建实测约 1ms/1,560 块（13k 块约十毫秒级）、
  向量矩阵装配 22ms、索引写盘 19ms —— 与 IndexFlatL2 的选择无关，无需更换索引结构。
- 解析侧早已增量（解析缓存命中，parse_ms 不含重新解析）。
- 冷态填一次向量缓存后进入稳态；稳态下**零次 Embedding 调用**。
- 稳态剩下的 6.1s 主要是：切分（全量，13k 块）+ BM25 倒排重建与 pickle 写盘 + 成对发布。

### 哪些环节仍是全量
1. **切分**：每次建库都对该学科全部资料重新分块（复用解析结果，但分块本身是全量）。
2. **FAISS 索引文件**：IndexFlatL2 全量写盘（向量复用，所以只花毫秒级）。
3. **BM25 索引**：倒排表与 pickle 全量重建（分词结果复用，跳过 jieba）。
4. **发布**：vector_store 与 bm25_index 成对切换（staging → 校验 → 2 次 rename）。
