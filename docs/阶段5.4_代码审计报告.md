## 二、发现的问题

### 【严重】P1: RAG向量库存储架构不一致 — RAG检索链路断裂

**文件**: `rag/rag_service.py`, `rag/vector_store.py`, `rag/hybrid_retriever.py`

**问题描述**:  
`build_knowledge`（构建）和 `retrieve_context`（检索）使用了完全不同的存储架构，导致RAG链路断裂。

**构建路径** (`rag_service.py` L137-152):
```
build_knowledge() → create_vector_store() → 创建内存ChromaDB → 返回成功
```
- `create_vector_store` 使用 `chromadb.Client()` 创建**内存中**的ChromaDB实例
- 不持久化任何FAISS索引文件到磁盘
- 构建API返回成功，但实际没有创建 `index.faiss` / `index.pkl`

**检索路径** (`rag_service.py` L265-346):
```
retrieve_context() → load_knowledge_base() → load_vector_store()
  → 检查 index.faiss 是否存在 → 不存在 → 返回空列表
```
- `load_vector_store` 检查 `index.faiss` 文件是否存在
- 文件不存在 → `vector_store = None` → 返回空列表
- Hybrid Retriever从未被正确初始化

**hybrid_retriever路径** (`hybrid_retriever.py` L168-203):
```
build_index() → GlobalFAISS.get() → add_documents() → 创建内存ChromaDB
  + build_bm25_index() → 构建BM25
```
- `hybrid_retriever.build_index` 从未被 `rag_service.build_knowledge` 调用
- 即使调用，也是创建内存ChromaDB，不持久化FAISS索引

**实际影响**:
- 文件上传 → ✅ 成功
- 知识库构建API → ✅ 返回成功（但内部使用错误存储）
- RAG检索 → ❌ 返回空结果（无FAISS索引文件）
- Chat端点 → ❌ 500错误（无RAG上下文 + LLM key无效）

**验证过程**:
```bash
# 1. 上传文件到math_001 → 成功
POST /api/knowledge/upload → 200

# 2. 构建知识库 → 返回成功
POST /api/knowledge/build → {"success": true, "chunks_count": 2}

# 3. 检查向量库文件 → 只有ChromaDB文件，无FAISS文件
ls data/vector_store/math_001/
→ chroma.sqlite3, data_level0.bin, header.bin... (ChromaDB格式)
→ 无 index.faiss, index.pkl (FAISS格式)

# 4. 测试chat → 500错误
POST /api/chat → 500 Internal Server Error
```

**修复建议**:  
统一存储架构。要么：
- **方案A**: `build_knowledge` 也使用FAISS（调用 `hybrid_retriever.build_index`），并持久化 `index.faiss` 和 `index.pkl`
- **方案B**: `retrieve_context` 和 `hybrid_retriever` 也使用ChromaDB持久化存储（替换FAISS检查逻辑）

### 【严重】P2: Health检查模块导入失败

**文件**: `api/app.py` L128-169

**问题描述**:  
启动时health检查报告 `llm: false` 和 `rag: false`，日志显示：
```
WARNING | Health check - LLM check error: cannot import name 'get_model_info' from 'llm'
WARNING | Health check - RAG check error: cannot import name 'VECTOR_STORE_DIR' from 'config'
```

**矛盾点**:  
命令行验证两个模块均可正常导入：
```python
>>> from llm import get_model_info  # ✅ 成功
>>> from config import VECTOR_STORE_DIR  # ✅ 成功
```

**可能原因**:  
FastAPI启动时模块初始化顺序问题。Health检查在startup事件中执行，此时某些模块可能尚未完全初始化。但由于顶层导入（`from config import settings`）成功，问题可能出在health检查代码的import方式。

**实际影响**:  
- Health端点返回 `llm: false, rag: false`（误导性状态）
- 但实际RAG模块可正常工作（知识库构建成功证明了这一点）

**修复建议**:  
将health检查中的import移到模块顶层（与其他import一起），避免在函数内动态导入。

### 【中等】P3: GlobalFAISS类存在重复方法定义

**文件**: `rag/vector_store.py` L424-481

**问题描述**:  
`GlobalFAISS` 类中 `count`、`add_documents`、`similarity_search` 三个方法各定义了两次：

| 方法 | 第一次定义 | 第二次定义 | Python行为 |
|------|-----------|-----------|-----------|
| `count` | L424-434 | L449-458 | 使用第二次定义 |
| `add_documents` | L436-440 | L460-474 | 使用第二次定义 |
| `similarity_search` | L442-447 | L476-481 | 使用第二次定义 |

**实际影响**:  
Python使用最后定义的方法，功能上不会出错。但：
- 代码可读性差，维护困难
- 第一次定义的 `add_documents`（L436-440）添加到现有store
- 第二次定义的 `add_documents`（L460-474）每次创建新store
- 如果开发者修改第一次定义，不会有任何效果

**修复建议**:  
删除重复的方法定义，保留正确的版本（第二次定义）。

### 【中等】P4: Chat端点LLM失败时返回500而非友好错误

**文件**: `api/routes/chat.py`, `services/ai_service.py`

**问题描述**:  
当LLM API key无效时，chat端点返回：
```json
{"success": false, "error": "Internal Server Error", "code": 500}
```

而education端点正确返回400：
```json
{"detail": "生成知识点总结失败: LLM调用失败: ..."}
```

**日志证据**:
```
ERROR | ai_service | LLM调用失败: Error code: 401 - Authentication Fails
WARNING | app | ValidationError: 生成知识点总结失败: LLM调用失败...
```

**问题链路**:
```
chat_service.chat_with_subject()
  → ai_service.chat_with_rag()
    → call_llm() → 401 AuthenticationError
      → raise ValidationError("LLM调用失败...")
        → 未被chat端点捕获 → 500通用错误
```

**实际影响**:  
用户看到"Internal Server Error"而非具体的错误提示。

**修复建议**:  
在chat端点添加 `ValidationError` 异常捕获，返回400状态码和具体错误信息。

### 【中等】P5: RAG检索失败时静默返回空结果

**文件**: `rag/rag_service.py` L327-346

**问题描述**:  
`retrieve_context` 中多处 `except` 块静默返回空列表：

```python
except Exception as e:
    logger.warning(f"知识库 {subject_id} 加载失败: {str(e)}")
    return []  # ← 静默返回空，不抛出异常
```

```python
except Exception as e:
    logger.error(f"检索失败: {str(e)}")
    return []  # ← 静默返回空
```

**实际影响**:  
- RAG检索失败时，AI服务收到空上下文
- AI仍会尝试调用LLM（浪费API调用）
- 用户不知道RAG失败，只看到LLM的"无上下文"回答

**修复建议**:  
RAG检索失败时应抛出明确异常，让上层决定是否继续（仅用LLM）或返回错误。

**好消息**: 
- 所有GET端点正常工作
- 文件上传功能正常
- 前端构建零错误，API字段匹配正确
- LLM模块代码结构完整（仅因placeholder key失败）
- 知识库管理（上传、删除、统计）功能正常

**需要修复**: P1（RAG存储统一）是阻塞性问题，修复后整个RAG链路即可正常工作。
